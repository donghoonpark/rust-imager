# rust-imager 개발 명세서

- 문서 상태: 구현 전 검토 초안
- 작성일: 2026-06-12
- 대상 플랫폼: Linux
- 구현 언어: Rust
- 사용자 인터페이스: 터미널 사용자 인터페이스(TUI)

## 1. 프로젝트 개요

`rust-imager`는 USB 리더를 통해 `/dev/sdX` 블록 장치로 노출된 외부 eMMC에서 부트 영역과 운영체제 파티션을 포함하는 복구 가능한 이미지를 빠르고 안정적으로 추출하는 Linux 전용 도구다.

전체 eMMC 용량을 그대로 읽는 대신, 지원되는 ext4 루트 파일시스템을 안전하게 축소하고 마지막으로 필요한 섹터까지만 순차적으로 읽는다. 추출 데이터는 Zstandard 또는 XZ로 실시간 압축한다. 복원된 이미지는 최초 부팅 시 systemd one-shot 서비스를 통해 루트 파티션과 ext4 파일시스템을 대상 장치의 가용 공간까지 자동 확장한다.

이 도구는 원본 eMMC를 읽기 전용으로 복제하는 프로그램이 아니다. 이미지 크기를 줄이기 위해 원본 eMMC의 파일시스템과 파티션 테이블을 직접 축소하며, 작업 완료 후에도 원본은 축소된 상태로 유지한다.

## 2. 목표

### 2.1 핵심 목표

1. USB 2.0처럼 느린 인터페이스에서 불필요한 빈 영역 읽기를 제거한다.
2. 디스크 읽기, 해싱, 압축, 파일 쓰기를 파이프라인화해 장치의 순차 읽기 처리량을 최대한 유지한다.
3. MBR, FAT 부트 파티션, ext4 루트 파티션으로 구성된 일반적인 Raspberry Pi 및 ODROID Linux 이미지를 인식한다.
4. 원본 변경 전 강한 안전 검사를 수행하고, 의심스러운 장치에는 명시적인 사용자 확인을 요구한다.
5. 추출 이미지의 무결성을 선택 가능한 검증 수준으로 확인한다.
6. 복원된 이미지가 최초 부팅 시 자동으로 저장장치 전체 크기를 사용하도록 한다.

### 2.2 성능 목표

- 추출 범위는 축소된 마지막 파티션의 끝을 포함하는 정렬된 마지막 섹터까지로 제한한다.
- 압축 및 해싱이 충분히 빠른 환경에서, 추출 처리량은 같은 장치와 범위에 대한 raw 순차 읽기 기준 처리량의 95% 이상을 목표로 한다.
- 고정 크기 버퍼 풀을 사용해 이미지 크기에 비례한 메모리 증가를 방지한다.
- 읽기 스레드가 압축 및 출력 단계와 독립적으로 동작하되, 메모리 제한을 넘으면 명시적인 백프레셔를 적용한다.

## 3. 비목표

초기 버전은 다음 기능을 제공하지 않는다.

- 현재 실행 중인 SBC의 내장 eMMC 추출
- `/dev/mmcblkN` 장치 직접 처리
- GPT 파티션 테이블 변경 또는 추출
- Btrfs, XFS, F2FS 등 ext4 이외 루트 파일시스템 축소
- NVMe, SATA 내부 시스템 디스크의 일반 백업
- 네트워크, SSH, S3, NAS 또는 마운트된 외장 저장소로 직접 출력
- 중단된 압축 스트림의 이어받기
- eMMC RPMB의 추출 또는 복원
- 리더가 별도 장치로 노출하는 eMMC boot0/boot1 영역 처리
- 이미지 복원 기능
- 실행 중인 파일시스템의 온라인 축소

## 4. 전제 조건

1. 프로그램은 Linux에서 `sudo`로 실행한다.
2. 대상은 USB 리더로 연결된 외부 eMMC이며 `/dev/sdX` 전체 디스크로 노출된다.
3. 리더는 필요한 부트 데이터를 포함한 전체 복원 가능 영역을 하나의 디스크 주소 공간으로 제공한다.
4. 지원 대상은 DOS/MBR 파티션 테이블이다.
5. 알려진 프로필은 FAT 계열 부트 파티션과 마지막 ext4 루트 파티션을
   포함한다. FAT가 없더라도 마지막 primary ext4 Linux 루트 등 안전
   필수조건이 충족되면 강한 경고와 정확한 model 확인 후 진행할 수 있다.
6. 루트 ext4 파티션은 오프라인 상태에서 축소할 수 있어야 한다.
7. 출력 파일은 프로그램이 실행되는 SBC의 내부 로컬 파일시스템에 저장한다.
8. 사용자는 작업 중 eMMC 리더와 호스트의 전원이 안정적으로 유지되도록 해야 한다.

## 5. 안전 모델

### 5.1 장치 선택 제한

- 전체 디스크 이름이 `/dev/sd[a-z]+` 형식인 장치만 후보로 표시한다.
- 파티션 경로(`/dev/sda1` 등)는 선택할 수 없다.
- 루트 파일시스템, `/boot`, swap 또는 현재 출력 경로가 속한 디스크는 후보에서 제외한다.
- USB transport로 확인되지 않는 장치는 기본적으로 제외한다.
- 장치 크기, vendor, model, serial, transport, removable 속성 및 파티션 목록을 TUI에 표시한다.
- 장치 식별 정보는 선택 시점과 변경 직전에 다시 읽는다. serial, major/minor 또는 크기가 바뀌면 작업을 중단한다.

### 5.2 파티션 구조 판별

장치 분석기는 다음 조건을 검사한다.

- 유효한 MBR 서명
- 보호 MBR 파티션 타입 `0xEE` 및 LBA 1의 GPT 헤더 부재
- 파티션 범위의 중첩 및 디스크 경계 초과 여부
- FAT 계열 부트 파티션과 보드별 파일 표식은 프로필 판별에 사용하며,
  없으면 `주의` 등급으로 처리
- 마지막 파티션이 ext4인지 여부
- 마지막 ext4 파티션이 MBR 기본(primary) 파티션인지 여부
- 루트 파티션에서 `/etc`, `/usr`, `/var` 등 Linux 루트 구조 확인
- Raspberry Pi 또는 ODROID 계열의 알려진 부트 파일과 파티션 특성
- 마지막 ext4 파티션 뒤에 보존해야 할 알려진 파티션이나 데이터가 없는지 여부

분석 결과는 `인식됨`, `주의`, `지원 안 됨`으로 분류한다.

- `인식됨`: 알려진 프로필과 필수 안전 조건을 만족한다.
- `주의`: MBR/마지막 primary ext4 필수 조건은 만족하지만 알려진
  FAT/보드 프로필과 다르다. 계속하려면 TUI에 표시된 장치 model 문자열을
  사용자가 직접 입력해야 한다.
- `지원 안 됨`: GPT, 중첩 파티션, 마지막 파티션이 ext4가 아닌 경우, 축소 대상이 논리 파티션인 경우 등 안전하게 처리할 수 없는 조건이다. 진행할 수 없다.

프로필 일치는 안전 보증이 아니라 추가 위험 신호를 제공하는 휴리스틱이다.

### 5.3 변경 전 조건

- 대상 장치의 모든 파티션을 자동 마운트 해제한다.
- 마운트 해제 실패, 프로세스 점유 또는 swap 사용이 감지되면 중단한다.
- 루트 ext4 파일시스템을 변경하기 전에 `e2fsck`를 실행한다.
- 자동 수정 가능한 오류만 정책에 따라 복구하며, 중대한 오류는 사용자에게 보고하고 중단한다.
- 출력 경로의 가용 공간을 예상 압축 크기와 무관하게 보수적으로 확인한다.
- 실제 변경 직전에는 장치 정보, 원본 용량, 예상 축소 용량, 출력 경로 및 "원본이 변경됨" 경고를 한 화면에 표시한다.
- 최종 확인에서는 장치 model 문자열을 다시 입력하도록 한다.

### 5.4 중단 및 실패 정책

작업 단계는 다음 두 범주로 구분한다.

- 안전 취소 가능: 분석, 마운트 해제 전, 출력 설정, 검증 설정
- 강제 종료 금지: 파일시스템 검사/수정, 파일시스템 축소, 파티션 테이블 변경

강제 종료 금지 단계에서는 일반 취소 입력을 거부하고 현재 작업의 완료를 기다린다. 프로세스 종료, 전원 차단 또는 장치 분리는 원본을 손상시킬 수 있다는 경고를 계속 표시한다.

추출 또는 압축 실패 시 부분 출력 파일과 로그는 보존한다. 재시도는 부분 파일을 이어 쓰지 않고 처음부터 시작하며, 새 출력 파일을 사용하거나 기존 부분 파일의 명시적 덮어쓰기 확인을 받는다.

## 6. 사용자 작업 흐름

TUI는 단계형 마법사로 구성한다.

1. **환경 검사**
   - root 권한과 필수 외부 도구 확인
   - 로컬 출력 파일시스템 여부 확인
2. **장치 선택**
   - 안전 필터를 통과한 `/dev/sdX` 목록 표시
3. **장치 분석**
   - 파티션 테이블, 파일시스템, 보드 프로필 및 위험 요소 표시
4. **위험 확인**
   - 비표준 구조 또는 최종 실행 전에 model 문자열 재입력
5. **출력 설정**
   - 로컬 경로, 파일명, Zstandard/XZ, 압축 레벨 선택
6. **검증 설정**
   - 검증 수준 선택
7. **실행 계획 확인**
   - 수행할 외부 명령, 예상 추출 범위와 원본 변경 사항 요약
8. **축소 및 추출**
   - 단계, 진행률, 처리량, 압축률, 경과/예상 시간 표시
9. **완료 보고**
   - 결과 파일, 크기, 해시, 검증 결과, 원본의 축소된 최종 크기 표시

키보드만으로 모든 작업을 수행할 수 있어야 하며, 작은 터미널에서는 핵심 상태와 경고를 우선 표시한다.

## 7. 처리 파이프라인

### 7.1 사전 분석

Rust 코어가 sysfs, `/proc`, `lsblk --json`, `findmnt --json`, `blkid` 및 파티션 메타데이터를 수집해 불변 실행 계획을 만든다. 외부 명령의 사람이 읽는 출력은 파싱하지 않고 JSON 또는 기계 판독 형식을 우선 사용한다.

실행 계획에는 다음 정보가 포함된다.

- 장치 identity와 전체 섹터 수
- 논리/물리 섹터 크기
- MBR 원본과 파티션 목록
- 부트 및 루트 파티션
- 루트 ext4 블록 크기와 사용량
- 축소 목표 블록 수와 안전 여유 공간
- 변경 후 파티션 끝 섹터
- 최종 이미지 읽기 바이트 수
- 선택한 압축 및 검증 정책

### 7.2 최초 부팅 확장 기능 삽입

루트 파티션을 임시로 읽기/쓰기 마운트해 systemd one-shot 서비스와 확장 스크립트를 설치한다.

확장 로직은 다음 원칙을 따른다.

1. `findmnt`, `lsblk`, `blkid`로 현재 루트 블록 장치와 상위 디스크를 동적으로 식별한다.
2. `/dev/mmcblk0p2` 같은 장치 이름이나 파티션 번호를 고정하지 않는다.
3. 실행 중인 루트 파티션이 디스크의 마지막 파티션인지 확인한다.
4. MBR에서 시작 섹터를 유지하며 루트 파티션 끝을 디스크 끝까지 확장한다.
5. 커널에 파티션 테이블 재인식을 요청한다.
6. 재부팅이 필요하면 다음 부팅에서 이어서 `resize2fs`를 수행한다.
7. 성공 후 서비스와 임시 상태를 제거하고 다시 실행되지 않도록 한다.
8. 기존 배포판 설정이나 `/etc/rc.local`을 수정하지 않는다.

상태 파일을 사용해 `partition-grow`, `filesystem-grow`, `cleanup` 단계를 멱등적으로 처리한다. 각 단계는 이미 완료된 상태에서도 안전하게 재실행할 수 있어야 한다.

### 7.3 ext4 및 MBR 축소

1. 확장 기능 삽입 후 루트 파티션을 마운트 해제한다.
2. `e2fsck`로 파일시스템을 다시 확인한다.
3. `resize2fs`를 사용해 최소 크기를 계산하고 안전 여유 공간을 포함한 목표 크기로 축소한다.
4. 축소 완료 후 ext4 메타데이터를 다시 검사한다.
5. `sfdisk`를 사용해 루트 파티션의 시작 섹터는 유지하고 끝 섹터만 줄인다.
6. 파티션 테이블을 다시 읽어 계획과 실제 결과가 일치하는지 검증한다.
7. 루트 파티션의 마지막 섹터 이후를 이미지 추출 범위에서 제외한다.

초기 안전 여유 공간은 `최소 256 MiB`와 `축소 후 ext4 크기의 5%` 중 큰 값으로 한다. 향후 측정 결과에 따라 기본값을 조정할 수 있지만, 첫 구현에서는 숨은 자동 최적화보다 보수적인 고정 정책을 우선한다.

### 7.4 이미지 추출과 실시간 압축

읽기 범위는 LBA 0부터 축소된 마지막 파티션 끝을 포함하는 정렬 경계까지다. 이 방식으로 MBR, 첫 파티션 앞의 raw 부트로더 영역, FAT 부트 파티션 및 ext4 루트 파티션을 함께 보존한다.

파이프라인은 다음 단계로 구성한다.

```text
block device reader
  -> bounded buffer pool
  -> optional SHA-256
  -> Zstandard or XZ encoder
  -> temporary output file
  -> fsync
  -> final output rename
```

- 기본 읽기는 큰 고정 블록의 순차 I/O를 사용한다.
- `O_DIRECT`는 정렬, 커널 및 USB bridge 호환성 검증 후 선택적 최적화로만 사용한다.
- 기본 구현은 page cache 오염을 줄이기 위해 순차 접근 힌트와 필요 시 cache drop 힌트를 사용한다.
- 정상 완료 전에는 `.partial` 접미사를 유지한다.
- 데이터 및 메타데이터 동기화가 완료된 뒤 최종 파일명으로 원자적 rename을 시도한다.

## 8. 압축

초기 지원 포맷은 다음 두 가지다.

- Zstandard: 기본값, 처리량 우선
- XZ: 저장 공간 우선

각 포맷은 `빠름`, `균형`, `최대 압축` 프리셋을 제공한다. 내부적으로는 Rust 라이브러리를 우선 사용해 진행률, 오류 전파 및 해싱 파이프라인을 통제한다. 압축 스레드 수는 호스트 CPU와 메모리에 따라 제한하며, 읽기 처리량을 방해하지 않도록 기본값을 정한다.

압축기가 입력을 따라가지 못하면 bounded queue가 백프레셔를 적용한다. 초기 버전은 실행 도중 압축 레벨을 자동 변경하지 않는다.

## 9. 검증 정책

검증은 실행마다 선택할 수 있다.

| 수준 | 동작 | 비용 |
| --- | --- | --- |
| 없음 | 압축 스트림 정상 종료와 파일 쓰기 성공만 확인 | 최소 |
| 스트리밍 SHA-256 | 추출 중 raw 데이터 SHA-256과 결과 메타데이터 기록 | 낮음 |
| 압축 무결성 | 결과를 다시 디코딩해 스트림 완전성과 raw SHA-256 일치 확인 | 중간 |
| 원본 재읽기 비교 | 축소된 원본 범위를 다시 읽어 SHA-256을 계산하고 디코딩 결과와 비교 | 높음 |

모든 성공 결과에는 JSON sidecar 메타데이터를 생성한다. 검증을 선택하지 않은 경우에도 검증 상태를 `not_performed`로 명시한다.

메타데이터에는 다음 내용을 기록한다.

- 도구 버전
- 실행 시작/종료 시각
- 원본 장치 식별 정보
- 원본 및 축소 후 크기
- 파티션 정보
- 압축 포맷과 설정
- raw SHA-256(해시를 계산한 검증 수준에서만 존재)
- 압축 파일 SHA-256(모든 성공 결과에서 기록)
- 검증 수준과 결과
- 자동 확장 서비스 버전

## 10. 아키텍처

Rust workspace는 다음 책임 경계를 갖는다.

### 10.1 `app`

- 프로세스 시작, root 검사, panic 처리
- TUI와 작업 엔진 연결
- 종료 코드와 최상위 오류 보고

### 10.2 `tui`

- 단계형 마법사 상태
- 사용자 입력, 경고 및 진행률 표시
- 장치 변경 로직을 직접 수행하지 않음

### 10.3 `device`

- sysfs와 `lsblk` 기반 장치 탐색
- 시스템 디스크 및 비 USB 장치 제외
- 장치 identity 재검증

### 10.4 `layout`

- MBR 파싱 및 검증
- FAT/ext4 파티션 식별
- Raspberry Pi/ODROID 프로필 판별
- GPT 감지 및 차단

### 10.5 `planner`

- 분석 결과를 불변 실행 계획으로 변환
- 축소 목표, 읽기 범위, 출력 공간 계산
- 변경 전후 invariant 정의

### 10.6 `system_tools`

- `e2fsck`, `resize2fs`, `sfdisk`, `mount`, `umount` 등 외부 도구 실행
- 명령 인자 구성, exit status 해석, stdout/stderr 캡처
- 테스트에서 가짜 실행기로 교체 가능한 trait 제공

### 10.7 `first_boot`

- systemd one-shot 파일 생성
- 대상 루트 파일시스템에 설치
- QEMU에서 독립 검증 가능한 확장 스크립트 관리

### 10.8 `pipeline`

- 블록 장치 순차 읽기
- 버퍼 풀과 백프레셔
- SHA-256, Zstandard/XZ, 출력 파일 처리
- 취소 가능 지점과 진행 이벤트 제공

### 10.9 `verify`

- 압축 스트림 디코딩 검사
- 원본 재읽기 및 해시 비교
- JSON sidecar 생성

### 10.10 `profiles`

- 알려진 보드/배포판 파티션 휴리스틱
- 프로필 데이터와 판별 근거 제공
- 프로필 불일치가 필수 안전 검사를 우회하지 못하도록 제한

## 11. 외부 도구

초기 구현은 검증된 Linux 도구를 Rust에서 통제하는 하이브리드 구조를 사용한다.

- `e2fsck`
- `resize2fs`
- `sfdisk`
- `lsblk`
- `findmnt`
- `blkid`
- `mount`
- `umount`
- `partprobe` 또는 동등한 커널 파티션 재인식 수단

시작 시 도구 존재 여부와 최소 기능을 검사한다. locale에 의존하는 텍스트 파싱을 피하고 가능한 경우 JSON, key-value 또는 명시적 exit code를 사용한다. 실행한 명령과 결과는 비밀 정보가 없는 범위에서 로그에 남긴다.

## 12. 오류 처리와 로그

- 내부 오류는 구조화된 오류 타입으로 분류한다.
- 사용자 오류, 지원하지 않는 레이아웃, 외부 도구 실패, I/O 오류, 압축 오류, 검증 오류를 구분한다.
- TUI에는 해결에 필요한 요약을 표시하고 상세 로그에는 명령, 단계, 장치 identity 및 stderr를 기록한다.
- 로그는 출력 이미지와 같은 기본 이름의 `.log` 파일로 로컬 저장한다.
- 장치 I/O 오류는 임의의 zero-fill로 대체하지 않고 즉시 실패 처리한다.
- 파일시스템 또는 파티션 변경 실패 후에는 자동으로 반대 작업을 시도하지 않는다. 현재 상태와 수동 복구에 필요한 정보를 보고한다.

## 13. 테스트 및 검증 계획

### 13.1 단위 테스트

- MBR 파서와 경계 조건
- GPT 보호 MBR 차단
- 파티션 중첩 및 overflow 검사
- 장치 후보 필터
- 보드 프로필 판별
- 축소 크기와 정렬 계산
- 실행 계획 invariant
- 외부 명령 exit status 해석
- systemd 확장 상태 머신
- 진행률 및 처리량 계산

### 13.2 합성 이미지 통합 테스트

작은 테스트 이미지를 생성해 다음 조합을 검사한다.

- MBR + FAT + ext4 정상 구조
- 비표준이지만 지원 가능한 구조
- GPT, 손상 MBR, 중첩 파티션
- 마지막 파티션이 ext4가 아닌 구조
- 손상된 ext4
- 빈 공간이 많거나 거의 없는 ext4
- 이미지 끝이 잘린 경우

loop device 또는 NBD로 파일을 실제 블록 장치처럼 노출하고 분석, 축소, 추출, 압축 해제 및 바이트 비교를 수행한다.

### 13.3 실제 배포 이미지 CI

초기 CI는 다음 공식 이미지 각 1종을 사용한다.

- Raspberry Pi OS 이미지 1종
- ODROID용 Ubuntu 이미지 1종

이미지는 저장소 Git 객체에 직접 포함하지 않는다. 공식 URL, 버전 및 SHA-256을 manifest에 고정하고 CI에서 다운로드한 뒤 캐시한다. URL 변경, 다운로드 실패 또는 SHA-256 불일치는 테스트 실패로 처리한다.

PR CI에서는 레이아웃 판별, 축소, Zstandard/XZ 추출, 압축 해제 및 파티션/파일시스템 검사를 수행한다. 이미지 버전 갱신은 별도 검토와 커밋으로 관리한다.

### 13.4 장애 주입

Linux block 계층을 이용해 다음 상황을 검증한다.

- 읽기 오류
- 간헐적 I/O 실패
- 매우 느린 장치
- 장치 분리와 유사한 영구 실패
- 출력 공간 부족
- 출력 파일 쓰기 오류
- 압축기 실패
- 검증 중 데이터 손상

`scsi_debug`, `dm-flakey`, `dm-dust` 또는 테스트 전용 block backend를 사용한다. 테스트가 호스트의 실제 디스크를 후보로 선택하지 못하도록 격리된 VM 또는 전용 CI runner에서 실행한다.

### 13.5 QEMU 최초 부팅 검증

QEMU 검증은 이미지 추출 자체보다 최초 부팅 자동 확장 기능을 대상으로 한다.

1. 축소된 테스트 이미지를 더 큰 가상 디스크에 기록한다.
2. 지원 가능한 ARM 또는 동등한 Linux QEMU 환경에서 부팅한다.
3. systemd one-shot이 루트 장치를 동적으로 식별하는지 확인한다.
4. 마지막 MBR 파티션이 가상 디스크 끝까지 확장되는지 확인한다.
5. 필요한 재부팅 후 ext4가 파티션 크기까지 확장되는지 확인한다.
6. 서비스와 상태 파일이 정리되고 다시 실행되지 않는지 확인한다.
7. 사전 배치한 파일의 해시와 부팅 성공 상태를 확인한다.

QEMU는 Raspberry Pi와 ODROID의 실제 SoC boot ROM, 펌웨어 및 USB eMMC 리더 동작을 완전히 재현하지 않는다. 보드별 부팅 호환성과 리더 특성은 실장비 테스트에서 확인한다.

### 13.6 실장비 승인 테스트

최소 다음 환경을 수동 또는 전용 runner에서 확인한다.

- Raspberry Pi 계열 공식 이미지가 설치된 eMMC와 USB 리더
- ODROID Ubuntu 이미지가 설치된 eMMC와 USB 리더
- USB 2.0 및 가능한 경우 USB 3.x 연결
- Zstandard와 XZ
- 네 가지 검증 수준
- 복원 후 실제 보드 최초 부팅 및 자동 확장

성능 보고에는 raw 순차 읽기 기준, 추출 범위, 압축 설정, 평균 처리량, CPU 사용률, 최대 메모리 및 결과 크기를 포함한다.

## 14. CI 단계

1. Rust format, lint 및 단위 테스트
2. 비 root 합성 이미지 테스트
3. 권한이 격리된 VM의 loop/NBD 통합 테스트
4. 실제 Raspberry Pi OS/ODROID 이미지 호환성 테스트
5. QEMU 최초 부팅 자동 확장 테스트
6. 성능 회귀 벤치마크

성능 벤치마크는 공유 GitHub-hosted runner의 절대 속도를 합격 기준으로 사용하지 않는다. 동일 실행 내 raw 기준 대비 상대 처리량을 기록하고, 안정적인 전용 runner가 준비되면 회귀 임계값을 적용한다.

## 15. 보안 및 권한

- 전체 프로그램이 root로 실행되므로 외부 명령 인자에 shell interpolation을 사용하지 않는다.
- 명령은 argv 배열로 직접 실행한다.
- 출력 경로의 symlink, 기존 파일, 디렉터리 traversal 및 소유권을 검사한다.
- 임시 mount point와 파일은 제한된 권한으로 생성한다.
- 대상 루트에 삽입하는 스크립트와 unit 파일은 빌드 시 고정된 자산으로 관리하고 해시를 기록한다.
- 다운로드하는 CI 이미지는 고정 SHA-256으로 검증한다.

## 16. 산출물 형식

성공 시 다음 파일을 만든다.

```text
<name>.img.zst 또는 <name>.img.xz
<name>.img.zst.json 또는 <name>.img.xz.json
<name>.img.zst.log 또는 <name>.img.xz.log
```

실패 시 압축 파일은 `.partial` 접미사를 유지하며 JSON sidecar는 성공 결과로 생성하지 않는다. 로그에는 실패 단계와 원본 변경 여부를 기록한다.

## 18. 완료 기준

초기 릴리스는 다음 조건을 모두 만족해야 한다.

- Linux에서 `sudo`로 실행되는 Rust TUI가 외부 USB `/dev/sdX`만 안전하게 표시한다.
- GPT와 지원하지 않는 레이아웃을 원본 변경 전에 차단한다.
- 알려진 FAT 부트 + 마지막 ext4 루트 또는 경고 승인된 ext4-root MBR
  이미지를 축소한다.
- 원본 eMMC는 축소 상태로 유지되고 파일시스템 검사를 통과한다.
- LBA 0부터 축소된 마지막 파티션 끝까지 Zstandard 또는 XZ로 추출한다.
- 선택한 검증 정책이 성공하고 JSON 메타데이터가 생성된다.
- 복원된 이미지가 QEMU와 지원 실장비에서 최초 부팅 후 루트 파티션을 확장한다.
- Raspberry Pi OS 1종과 ODROID Ubuntu 1종의 고정 공식 이미지 CI가 통과한다.
- USB 2.0 실장비에서 raw 순차 읽기 대비 목표 처리량을 측정하고 결과를 문서화한다.

## 19. 알려진 위험

1. 원본 직접 축소 중 전원 차단이나 장치 분리는 파일시스템을 손상시킬 수 있다.
2. USB bridge가 flush 또는 오류를 올바르게 전달하지 않을 수 있다.
3. 보드별 raw 부트로더 위치가 일반 파티션 구조와 다를 수 있다.
4. 실제 배포 이미지의 파티션 구조가 업데이트로 변경될 수 있다.
5. systemd 최초 부팅 단계에서 루트 파티션 테이블 재인식에 재부팅이 필요할 수 있다.
6. 최소 ext4 크기 계산과 실제 축소 가능 크기는 e2fsprogs 버전에 따라 달라질 수 있다.
7. XZ 고압축 설정은 저성능 SBC에서 USB 2.0 읽기보다 느려 전체 처리량을 제한할 수 있다.
